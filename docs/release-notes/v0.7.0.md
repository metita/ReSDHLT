Three new diagnostics and an optional Vulkan backend for RAD's lighting.

## Lightmap atlas budget

GoldSrc packs every lit face into 64 pages of 128x128 luxels and aborts the map load with `AllocBlock: full` when they do not fit. That used to be found out after a full compile, or in game.

RAD now runs the engine's own allocator before it creates a single direct light. Past 95% of the budget it prints a breakdown by texture ranked by lightmap footprint, so the textures worth rescaling are named. Over the limit it stops with an error rather than spend forty minutes lighting a map that cannot load. `-noallocblockcheck` compiles anyway.

```
!!! ERROR: LIGHTMAP ATLAS OVERFLOW - map exceeds the engine's 64 page limit
    usage    71 / 64 pages (111%)
    cause    too many lightmapped luxels, so the engine aborts with "AllocBlock: full"
    action   raise the texture scale on the biggest consumers below, or make them smaller

    Lightmap atlas budget by texture (top consumers):
      texture                  faces       luxels  % budget
      --------------------------------------------------------------
      dev_r3_cs2y2             2,258      242,850     72.0%
      dev_c3_dhmsl0            1,702      119,917     36.6%
```

BSP gains `-lmoptimize`, off by default. The allocator is first fit in face order and never backtracks, so the order faces happen to be written in is worth a page or two on a full map. Three legal orders are measured against that same allocator and the fewest-pages one is kept, so the result can never be worse than before.

## Leak diagnostics that point at the hole

The pointfile used to be a side effect of the outside flood fill. It recorded whatever order the recursion happened to unwind in, so it wanders across the map, doubles back, and nowhere marks the place where the inside actually opens onto the void.

The trail is now built separately once the leak is proved, as a shortest path over the portal graph from the leaked entity out, simplified so the `.lin` file is a handful of clean segments instead of one per portal crossed. The hole itself is identified rather than guessed: a second flood marks the region that is unambiguously outside, and the hole is the first portal on the path that leads into it. Its coordinates are printed and a dense marker star goes into the `.pts`.

Every hull that leaks now feeds one report at the end of the compile instead of repeating the same warning up to four times. `-allleaks` walks every hole rather than the first one found, so a leaky map can be sealed in one pass through the editor.

## Optional GPU lighting

`-gpu` runs RAD's direct light gathering as Vulkan compute, off by default.

Whether it helps depends on how many direct lights the map has, because that is the dimension a GPU parallelises over. Same room, same settings, only the light count changing, GTX 1060 against six CPU threads with `-extra`:

| lights | CPU | `-gpu` | speedup |
|---:|---:|---:|---|
| 1 | 0.66s | 1.32s | 0.50x, slower |
| 256 | 1.59s | 1.29s | 1.23x |
| 512 | 2.27s | 1.31s | 1.73x |
| 1024 | 3.91s | 1.72s | 2.27x |

CPU time grows linearly with the light count. Time on the device barely moves across a 1024x increase. The crossover sits around 150 to 200 lights.

BuildFacelights is split in two halves that each run once, so nothing expensive is computed twice: the first records the gather calls, the device answers them all at once, and the second drops each answer where the CPU gather would have written it. Output is byte identical to the CPU path on almost everything measured, the one exception differing by a single byte in 95,982 by one step out of 255.

It hands the work back to the CPU, saying why, when the map has opaque entities, studio model shadows, more light styles than the kernel has slots, a BSP deeper than its traversal stack, or when no Vulkan driver is present. Building it needs no Vulkan SDK.
