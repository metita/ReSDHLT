ReSDHLT 0.23.0 brings the `info_portal` rework from SDHLT 1.3.1 into VIS. Maps
that do not use `info_portal` compile exactly as before.

Thanks to @seedee, who wrote the rework in SDHLT, answered questions about it
and pointed out the one thing to watch when porting it: brush entity origins.

## Highlights

- VIS: `info_portal` can target any entity with a `targetname`. `info_leaf` is
  gone, use an `info_target` or any other entity instead.
- VIS: a brush entity as the target links every leaf its faces touch, so a
  whole building or room can be forced visible (or sealed) with one entity. The
  entity origin is taken into account, which upstream does not do yet.
- VIS: `target` accepts several names separated by semicolons.
- VIS: `neighbor` grows layers of leaves around the `info_portal` and the new
  `targetneighbor` grows them around the target, up to 16 each.
- VIS: `reverse` seals the leaves off instead of opening them, and `oneway`
  limits the link to the `info_portal` side. Links are now two-way by default.
- VIS: a warning when a brush entity's bounding box overlaps more than 48
  leaves, because the engine then falls back to a coarser visibility test.

## Fixed

- VIS: several `info_portal` in the same leaf no longer overwrite each other's
  `neighbor` depth, a missing target no longer links a bogus leaf, and the links
  survive `-maxdistance`.

## Updating

`tools/sdhlt.fgd` has the new keys. A map that used `info_leaf` needs its
`info_portal` retargeted to an entity with a `targetname`, otherwise the link
is dropped with a warning.
